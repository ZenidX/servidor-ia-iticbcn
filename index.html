Servidor de IA del ITICBCN

Una propuesta para que el servidor de GPUs del centro dé servicio de modelos de lenguaje a las clases, aloje nuestras aplicaciones y sostenga el I+D+i, de forma estable, segura y sin que nadie tenga que entrar en la máquina.

Xavi Lara · Coordinador DUAL & I+D+i

01Para qué es el servidor

Proponemos que sirva para tres cosas, por este orden:

  1. Servicio de LLM al centro. Un chat y una API de modelos de lenguaje para las actividades de clase, que pueda usar el profesorado y el alumnado sin depender de servicios externos ni de cuentas personales.
  2. Alojar nuestras aplicaciones, como CoorDUAL (la gestión de la FP Dual) y las que vengan. Los datos personales del alumnado se quedan dentro del centro.
  3. I+D+i: modelos de vídeo e imagen para contenido propio del ITIC (ya aprobado) y entrenamiento o fine-tuning en proyectos de clase.

Principio: nadie se conecta al sistema operativo salvo para montar y configurar servicios. Profesorado y alumnado lo usan solo por web y por API.

03Cómo está montado ahora

  • Windows 11 Pro de escritorio como sistema base, con Ubuntu dentro de WSL.
  • Una cuenta de administrador compartida por la que entra quien necesita algo.
  • Dos Ollama, uno en Windows y otro en WSL, que se disputan el mismo puerto con modelos distintos.
  • Open WebUI (el chat) lanzado a mano; tras un reinicio no vuelve solo.
  • Proyectos de compañeros en carpetas dentro del Ubuntu de WSL.

En las últimas semanas ya se ha montado el acceso remoto de administración por un túnel cifrado (SSH solo con clave, ningún puerto abierto a internet), ComfyUI para el I+D+i de vídeo como servicio en la GPU 1, y CoorDUAL en contenedores con su base de datos y su repositorio git en el propio servidor.

Problemas de este montaje

  • FrágilLos servicios dependen de una sesión de Windows abierta. Un reinicio por actualizaciones deja al centro sin chat.
  • No escala a una claseOllama atiende bien a una persona; con 25-30 alumnos a la vez las respuestas se encolan.
  • Sin control de usoNo hay claves por grupo, ni cuotas, ni registro de quién usa qué.
  • InseguroUna cuenta compartida da acceso total, y el escritorio invita a "entrar a mirar".
  • Sin copiasUn único disco. Si falla, se pierden chats, modelos y la base de datos de CoorDUAL.
  • A ciegasSin monitorización ni rastro de cambios: nadie sabe si algo ha caído ni qué se tocó.

04Propuesta

Un servidor Linux sin escritorio. Todo corre en contenedores, se entra solo por web o API, y la configuración vive en un repositorio git.

Sistema operativo: Ubuntu Server 24.04 LTS

  • Las herramientas de GPU son de Linux. vLLM, NVIDIA Container Toolkit y la monitorización de GPU funcionan de forma nativa; sobre WSL van peor y con más limitaciones.
  • Servicios que arrancan solos tras un reinicio, sin que nadie inicie sesión.
  • Sin escritorio, no hay nada que abrir.
  • No hay alternativa razonable en Windows: pasar las GPUs a una máquina virtual Linux solo existe en Windows Server, no en Windows 11 Pro.

Reparto de las GPUs

  • GPU 0, siempre: el LLM de clase. No se toca.
  • GPU 1, flexible: un segundo modelo (código o multimodal), vídeo, entrenamiento y fine-tuning.
  • Las dos juntas solo en ventanas planificadas, para un modelo grande.

No hay cuentas compartidas. Los cambios se hacen en el repo infra-super y se aplican con docker compose up: cada cambio queda con autor, fecha y vuelta atrás.

Datos y RGPD

  • Los datos no salen del centro. Conversaciones del chat y datos de aplicaciones (CoorDUAL tiene datos del alumnado) se quedan en el servidor.
  • Copias cifradas, con la copia externa en un destino del centro (NAS o Drive institucional).
  • Registro mínimo: LiteLLM guarda el consumo por clave, no el contenido.

Es un buen argumento frente a usar servicios externos de IA con el alumnado.

07Plan de migración

  1. Inventario y copia de usuarios y chats de Open WebUI, modelos, proyectos de compañeros y la base de datos de CoorDUAL.
    ½ día
  2. Hablar con quien usa hoy la máquina para dar sitio a sus proyectos en la nueva arquitectura.
    —
  3. Reinstalar con Ubuntu Server, drivers NVIDIA, Docker y el túnel.
    ½ día
  4. Montar el repo infra-super: proxy, LiteLLM, vLLM, Open WebUI, monitorización y copias.
    1-2 días
  5. Restaurar Open WebUI, CoorDUAL y ComfyUI como stacks.
    ½ día
  6. Prueba de carga con un grupo real y ajuste de cuotas.
    1 sesión

Casi todo se hace en remoto. El corte de servicio se limita a la reinstalación.

08Qué necesitamos decidir

  • Aprobar la reinstalación con Ubuntu Server.
  • Subdominio del servicio, y si el chat se abre fuera del centro o solo dentro.
  • Política de uso: cuotas por alumno y quién puede usar las dos GPUs.
  • Administradores: quién, como máximo dos personas.
  • Un segundo NVMe de 2-4 TB para copias y modelos: la mejora de hardware más rentable (unos 150-300 €).
  • Opcional: ampliar la RAM (quedan 4 ranuras) para más contenedores o modelos en CPU.
